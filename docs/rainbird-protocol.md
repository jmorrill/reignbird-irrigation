# Rain Bird LNK / LNK2 WiFi Local Protocol

The local network protocol spoken by Rain Bird's LNK and LNK2 WiFi modules. Rain Bird
publishes no specification for it.

This document is the protocol reference for this project, and everything in it has
been checked against a physical controller — an ESP-ME3, model `0009`, protocol 2.12,
firmware 3.11. Where it differs from the community `pyrainbird` / `node-rainbird`
libraries, this document wins: those describe an older firmware generation, cover
roughly a third of the command surface, and several of their assumptions are untrue
on current hardware. Section 9 says how each claim here was verified.

---

## 1. Transport

The LNK module speaks **JSON-RPC 2.0 over an encrypted HTTP body**.

| | |
|---|---|
| Endpoint | `POST http://<controller-ip>/stick` (port 80) |
| TLS variant | `POST https://<controller-ip>/stick` (newer firmware; self-signed, pinned) |
| Content-Type | `application/octet-stream` (encrypted) / `application/json` (plaintext, setup only) |
| Extra header | `Connection: keep-alive` |
| HTTP version | Forced HTTP/1.1 (`RBJSONOkClient.createOkHttpClient`) |
| Timeouts | 30 s connect/read/write; 120 s "extended" for firmware ops |

Source: `rpc/RBJSONOkClient.createHttpRequest`, `rpc/RPCRequestManager.setCurrentTargetIP`.

### 1.1 Alternate transports

A controller can be reached three ways. Only the first is needed for local-only
control, and it is the only one this project implements.

1. **Direct LAN** — `http://<ip>/stick`, as above.
2. **AP / provisioning mode** — the controller raises its own SSID
   `RAINBIRD<last-6-of-MAC>`; same `/stick` endpoint, usually unencrypted while the
   password is still being set (`isControllerOnAP`).
3. **Cloud relay** — WebSocket `wss://rbcloud.rainbird.com/<controller-key>`, or
   `ws://<host>:80/<controller-key>` for a self-hosted relay. Identical JSON-RPC
   payloads, same encryption. Set via `setRemoteTargetIP`.

Discovery on the LAN is a UDP broadcast: replies are matched against the controller's
MAC and serial number.

## 2. Encryption

**AES-256-CBC, zero-padded, with a SHA-256 integrity prefix.** Note this is
AES-**256** (a 32-byte key), not AES-128 as sometimes reported.

### Key derivation

```
key = SHA256(password_utf8)          // 32 bytes
```

The "password" is the controller's device password, held in
`RPCRequestManager.controllerKey`.

### Request (app → controller)

```
plaintext = <json-rpc request, UTF-8>
padded    = plaintext + 0x00 * (16 - len % 16)   // zero pad to AES block, no PKCS7
iv        = <16 random bytes, generated by the Cipher>
body      = SHA256(plaintext)  ||  iv  ||  AES256-CBC-Encrypt(key, iv, padded)
             \_____32 bytes___/    \_16_/
```

The pad is zero-fill to the next 16-byte boundary, and the hash is plain SHA-256.

> The SHA-256 in the prefix is computed over the **unpadded** plaintext.

### Response (controller → app)

```
hash       = body[0  : 32]
iv         = body[32 : 48]
ciphertext = body[48 : ]
plaintext  = AES256-CBC-Decrypt(key, iv, ciphertext)
plaintext  = plaintext.strip("\0")           // remove zero padding
assert SHA256(plaintext_including_padding) == hash   // see note
```

### The hash is asymmetric — this matters

The two directions do **not** use the same convention, and a client that assumes they
do will fail on roughly fifteen out of every sixteen messages.

| Direction | What the hash covers |
|---|---|
| App → controller (`encryptRequest`) | `SHA256(plaintext)` — **unpadded** |
| Controller → app (`decryptRequest` verifies) | `SHA256(decrypted string incl. trailing NULs)` — **padded** |

In `decryptRequest` the decrypted buffer is converted to a UTF-8 `String` *before*
hashing and only *afterwards* has its NULs stripped, so the padding is inside the
hash. `encryptRequest` hashes the plaintext directly, before padding.

The asymmetry is invisible whenever a payload happens to be an exact multiple of 16
bytes, which is why it is easy to miss — and why implementations that only ever
tested against block-aligned frames appear to work.

**Recommendation for a client:** send hashing the unpadded plaintext, and when
verifying a response accept *either* hash. Accepting both is not
a weakening: the prefix is an unkeyed SHA-256 sent in the clear, so it cannot
authenticate against an active attacker. Its real function is to tell you the password
was wrong, and both forms answer that equally well. Rejecting a controller whose
firmware chose the other convention is a far worse failure mode than accepting both.

Verification is skipped entirely during provisioning, while the password is still
being set.

## 3. JSON-RPC envelope

`rpc/RBJSONRPCClient` builds:

```json
{
  "id": <random int>,
  "jsonrpc": "2.0",
  "method": "<rpc method>",
  "params": { ... }
}
```

Responses carry the matching `id` plus `result` or `error`.

## 4. RPC methods

From `rpc/RPCCall` and `rpc/RPCRequestManager`. Methods marked **local** are served
by the LNK module itself; **cloud** ones go to Rain Bird's servers and are out of
scope for a local-only app.

### 4.1 The tunnel

| Method | Params | Notes |
|---|---|---|
| `tunnelSip` | `{"length": <bytes>, "data": "<hex>"}` | **local** — wraps a raw SIP command (§5). `length` is `data.length / 2`. |

code. `00` means NAK (`RPCTunnelSIP.checkForNak`).

The single most useful poll — one round trip gives the whole dashboard.

| Field | Offset (nib) | Len (nib) |
|---|---|---|
| hour | 2 | 2 |
| minute | 4 | 2 |
| second | 6 | 2 |

## 6. Schedule read/write (SIP `20` / `21`)

The schedule is not a single blob — it is a set of **pages**, each read with
`20 00 <page>` and written with `21 00 <page> <data>`.

The community tables stop at "there is a schedule command". The full page map below
is what makes schedule *editing* possible.

### Page map (ESP-ME / ESP-ME3 family)

| Page | Contents |
|---|---|
| `0` | Global info |
| `15 + n` | Program `n` info |
| `95 + n` | Program `n` start times |
| `128 + ⌊(s−1)/2⌋` | Run times for the **station pair** `(2k+1, 2k+2)` |

`n` is the 0-based program index; `s` is a 1-based station number. `getRunTimePages()`
returns 11 for this family, so pages `128`–`138` cover stations 1–22.

### Page 0 — global info

| Field | Width |
|---|---|
| Inter-station delay | 2 bytes |
| Snooze | 1 byte |
| Rain sensor bypass | 1 byte — `0` = sensor active, `1` = bypassed |

### Page `15 + n` — program info

| Field | Width | Notes |
|---|---|---|
| Custom days bitmask | 1 byte | 7 day flags |
| Cyclic days | 1 byte | interval for cyclic frequency |
| Days remaining | 1 byte | countdown to the next cyclic run |
| Permanent days off | 1 byte | |
| Seasonal adjust | 1 byte | a literal `100` means "no adjustment" |
| Frequency type | 1 byte | see below |

**Frequency type:**

| Value | Meaning |
|---|---|
| `0` | Custom days (use the day bitmask) |
| `1` | Cyclic (every N days) |
| `2` | Odd days |
| `3` | Even days |

### Page `95 + n` — start times

`maxStartTimes` consecutive **16-bit** values, each *minutes from midnight*
(`%04X`). Per-model counts are in §7 — 6 for the ESP-ME3, 4 for the ESP-TM2.

### Pages `128 + ⌊(s−1)/2⌋` — run times

Each page carries **two stations**, the odd-numbered one first. For each station, one
**16-bit run time in minutes per program**, in program order — so
`maxPrograms × 2` bytes per station:

```
page 128:  [station 1: prog A, B, C, D]  [station 2: prog A, B, C, D]
page 129:  [station 3: ...]              [station 4: ...]
```

For an ESP-ME3 (`maxPrograms` = 4) that is 8 bytes per station, 16 bytes per page.

**Disabling a station** is not a separate flag: `generateStationDisablePage` writes
the same page layout with **all-zero run times** for the disabled station. A station
with no run time in any program simply never waters.

### Other model families

`generateTM2ProgramRunTimePage` handles the ESP-TM2 family, which packs run times
differently; `RZXSIPProcessing` and `ST8SIPProcessing` implement the same interface
for the non-program-based models, which schedule per zone rather than per program.
This is why `ControllerType` carries `maximumAvailablePrograms`, `maximumStartTimes`
and `maximumAvailableStationPages` (§7) — the page layout is derived from them.

**out of scope** for this project — no HTTP endpoint exists for them.

## 8. Practical notes for a client implementation

- **Serialise everything.** The controller handles one request at a time. Use a
  single-threaded queue and a 50 ms gap between posts; concurrent requests produce
  503s.
- **Retry policy that works:** on `IOException` retry after 1500 ms (max 3); on
  HTTP 503 retry after 50 ms (max 3); after 3 timeouts, disconnect.
- **Poll with `4C`,** not a fan of individual getters — one command returns time,
  date, rain delay, sensor state, irrigation state, seasonal adjust, remaining
  runtime and active station.
- **Station bitmasks** (`83`, `BF`) are paged; page 0 covers stations 1–32.
- **Wrong password** surfaces as a decryption/hash-mismatch failure, not an HTTP
  error. There is no "unauthorised" status; the response simply will not decrypt.
- **`CommandSupportRequest` (`04`)** lets a client feature-detect before offering
  flow monitoring, statistics or schedule editing on an unknown model.

## 9. Verification

Every claim in this document was checked against a physical **ESP-ME3** (model
`0009`, protocol 2.12, firmware 3.11) over the LAN. The frames that document each
behaviour are kept as test cases in
`src/RainBird.Protocol.Tests/HardwareBehaviourTests.cs`, so a change that breaks one
of these findings fails the build rather than silently regressing.

Behaviour on other model families — ESP-TM2, RZXe, ST8x — is handled by capability
probing rather than assumption, and has not been exercised against hardware.
